# Shrinovva Homeophatic

A responsive Flutter clinic workspace with fictional patient data and in-memory demo state.

## Run

```sh
flutter pub get
flutter run -d chrome
```

Staff and doctor sign-in require Firebase Authentication email/password accounts and matching Firestore profiles (`staff/{uid}` or `doctor/{uid}`). Select the assigned role on the login screen. Both roles can view and register patients, which are saved in Firestore. Consultation tickets and drafts are saved in the Firestore `tickets` collection.

## Android staff authentication setup

1. Open the Firebase project where you created the staff account.
2. In **Project settings > Your apps**, add or select the Android app with package name `com.example.rmc_clinic_health`.
3. Download its `google-services.json` and save it to `android/app/google-services.json`. Use the client configuration file, not a service-account private key.
4. In **Authentication > Sign-in method**, enable **Email/Password**. Confirm the staff account appears in **Authentication > Users**; a Firestore document alone does not create a login account.
5. Stop the running app and run `flutter run` on the Android emulator again. Native Firebase configuration requires a rebuild; hot reload is insufficient.

The Google Services Gradle plugin loads that configuration during the Android build. Android builds require this file. Web and Windows Firebase configuration must be set up separately before staff sign-in works on those platforms.

## Client web preview

The workflow in `.github/workflows/deploy.yml` builds the Flutter web app and deploys it to GitHub Pages whenever you push to `main`. You can also run **Deploy UI preview** manually from the repository's **Actions** tab.

1. In GitHub, open **Settings > Pages** and set **Build and deployment > Source** to **GitHub Actions**.
2. Commit and push the project, including the workflow, to `main`.
3. Wait for **Deploy UI preview** to finish in **Actions**, then open the deployment URL.

For the current repository, the default preview URL is https://devajsanpablo.github.io/shrinova_clinic/ . It becomes available after the first successful deployment. The workflow handles the Pages base path and uses Flutter 3.47.0, matching the development SDK. No extra deployment secrets are needed.

The web preview displays the login UI, but sign-in requires separate web Firebase configuration. Patient registrations use Firestore; consultation tickets and their completion notes also persist in Firestore.

## UI

- Inter typography through [google_fonts](https://pub.dev/packages/google_fonts) 8.2.1.
- Short, one-shot entrances through [flutter_animate](https://pub.dev/packages/flutter_animate) 4.5.2; OS reduced-motion preferences are respected.
- A brief branded startup screen with animated dots from [flutter_spinkit](https://pub.dev/packages/flutter_spinkit) 5.2.2 fades into login and respects reduced-motion preferences.
- Original, bundled healthcare SVG illustrations rendered with [flutter_svg](https://pub.dev/packages/flutter_svg) 2.3.0.
- Responsive desktop sidebar, tablet navigation rail, and mobile navigation.
- Searchable patient directory and queue, status filters, visible primary actions, responsive patient summaries, and allergy alerts.
- Fonts and illustrations load from local assets. Google Fonts runtime downloading is disabled.

## Structure

```text
lib/
  core/       # Shared theme and session state
  data/       # Fictional patients and tickets
  models/     # Patient, visit, role and ticket models
  screens/
    doctor/   # Doctor-only consultation screen
    staff/    # Reserved for staff-only screens (see its README)
    shared/   # Screens accessible to both staff and doctors
  widgets/    # Reusable cards, summaries, illustrations and motion
assets/
  fonts/          # Bundled Inter font files and SIL Open Font License
  illustrations/  # Original vector artwork
test/             # Smoke and responsive layout checks
tool/             # Optional rendered preview generation
```

## Ticket persistence

`lib/model/ticket.dart` defines the ticket fields from the consultation form: patient ID, complaint, consultation reason, symptoms, optional vital signs, assigned doctor, priority, and notes, plus queue reference, creation time and status. Firestore adds the authenticated creator and server save timestamp. Document IDs are generated by Firestore; queue references use `Q-` followed by that ID and are not sequential numbers.

Registration saves the patient first, then opens the same ticket form with the patient and symptoms selected. A ticket is saved only after the visit details are reviewed. Failed submissions retain their ID and original contents for retry. Login reloads patients and tickets. Doctor status changes and completed consultation notes persist on the ticket; patient history is reconstructed from those notes on login. Doctor names currently come from the existing form options, not doctor account IDs.

Ticket reads and creation require a staff or doctor profile. Only doctors can start or complete consultations; completed tickets cannot be changed or deleted. Existing patient and account rules are retained.

Test rules locally (Java 21+ required):

```sh
firebase emulators:exec --only firestore --project demo-clinic "node tool/test_ticket_rules.mjs"
```

Deploy rules to the configured Android Firebase project:

```sh
firebase deploy --only firestore:rules --project clinic-86788
```
